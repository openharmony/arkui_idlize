## 处理管线

IDLize 中的一般执行路线通常如下：

```
                   生成器 1 (TS 代码)
                 /
 .d.ts -> IDL IR -> 生成器 2 (ArkTS 代码)
 .idl -----^     \
                   生成器 3 (C++ 代码)
```

生成器了解要生成代码的风格和运行时语义，通常由库维护者开发和调优。

## 限制

这种架构在支持原始 TypeScript 语言的所有语法构造方面存在一定限制。
部分原因来自 IDL 有意限制的表达能力，但总体而言，这是由目标应用模型的
多语言多运行时特性所决定的。如果输入已经是 IDL 格式，
其表达能力决定了可以和不可以表达的内容。

也就是说，所有假设特定编程语言特性的东西 — 其对象模型、数据结构、
并发模型等 — 最好排除在 IDL IR 之外，因为 IDL IR 的目的仅仅是定义接口。
以下 TypeScript 构造在 IDL 中不太可能有太多表示：
   * 泛型，因为不同语言中泛型类型的确切机制各不相同，无法在语言运行时之外表达。
   我们仍然提供类似泛型的预定义语法构造，如 `sequence<Foo>` 或 `record<string, Bar>`，
   如果需要还可以提供更多，但不给用户定义自定义泛型构造的能力
   * 交叉类型，因为这种信息在定义跨语言接口时通常是多余的，只在某些语言中有意义
   * 真正的多态对象，即子类实例作为父类传递的情况，
   重要的情况如 Context 或 FrameNode 由生成器特殊处理
   * TypeScript 的特定类型，包括以下种类：
      * `any`、`unknown` 等类型
      * 非常特定于语言的类型和类型构造，如签名类型、`typeof` 等
      * TypeScript 标准库类型（可能排除少数允许的类型，如 `number`、`Date`），
      取而代之的是一组具有可预测映射到可能运行时实现的内建 IDL 类型，
      即目前至少有 `i8, i16, i32, i64, f32, f64, Object, string, buffer`
   * 与接口相关的概念仍然可以在 IDL 中表示，例如 `async` 关键字或 `[Throws]` 扩展属性

对于每种情况，都应定义翻译策略来处理这些构造，直到我们在 .d.ts 文件定义中
消除它们或完全切换到 IDL。
